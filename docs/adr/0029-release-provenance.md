# 0029. Releases: tag-triggered workflow, GitHub artifact attestations, own SBOM

- Status: accepted
- Date: 2026-10-26

## Context

Security requirements (docs/security.md, supply chain): signed releases and images, SBOM, reproducible builds where
possible, provenance. Operators must be able to check that an image was built from a given tag of this repository by
its release workflow, without trusting the registry or a maintainer's laptop.

## Decision

- A release is a signed tag `vX.Y.Z` pushed by a maintainer (`git tag -s`). The tag starts
  `.github/workflows/release.yml`, which first runs the whole CI workflow (reused via `workflow_call`) and then
  publishes. It can be gated by required reviewers on the `release` environment.
- The image is built for `linux/amd64` and `linux/arm64` with the BuildKit CLI preinstalled on the runner (BuildKit
  image pinned by digest) and pushed to `ghcr.io` under the exact version only, never `latest`.
- Provenance and SBOM are **GitHub artifact attestations** (`actions/attest`, Sigstore keyless signing with the
  workflow's OIDC identity), attached to the image digest in the registry and in the GitHub attestations API.
  Operators verify them with `gh attestation verify` (repository, signer workflow, source tag). BuildKit's own
  unsigned attestations are disabled. No separate cosign signature: the attestation already binds a signed statement
  to the digest, and one tool verifies everything; there are no long-lived signing keys to protect.
- The SBOM is SPDX 2.3, generated by `scripts/sbom.ts` from `npm query .prod` (the set the license check uses), the
  lockfile integrity hashes and the pinned Node base image. `npm sbom --omit dev` was rejected: with this lockfile it
  silently drops runtime packages that dev dependencies also require (`pg-types`, `postgres-*`, …), and on a
  production-only tree it fails.
- Builds are reproducible (`SOURCE_DATE_EPOCH` = commit time, `rewrite-timestamp=true`, see
  [ADR-0028](0028-container-image.md)): anyone can rebuild a tag and compare the image digest.
- Third-party code in the release path is limited to GitHub-owned actions pinned by commit SHA (`checkout`,
  `setup-node`, `attest`, and since [ADR-0033](0033-release-isolated-signing.md) `upload-artifact` /
  `download-artifact`); Docker and the GitHub release use the runner's CLIs. Signing runs in its own job
  (ADR-0033).

## Consequences

- Attestations need a public repository (or GitHub Enterprise Cloud) and are tied to GitHub's Sigstore setup.
- The package is not published to npm (`private: true`); the container image is the release artifact.
- Tag signatures are a maintainer practice, not enforced by the workflow; the attestation's source ref and digest
  are what operators check.
